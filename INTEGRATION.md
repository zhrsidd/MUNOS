## Database

24 public tables: conferences, committees, schools, staff, conference_staff, committee_staff, sessions, delegates, user_access, attendance, scoring_definitions, documents, document_versions, document_comments, archive_jobs, participation_events, participation_corrections, speaker_queue, timers, votes, award_criteria, award_scores, audit_log and operational_changes. Private tables: access_credentials and mutation_receipts.

UUID keys, composite foreign keys constrain conference/committee relationships, attendance is unique per delegate/session, active queue entries are unique, and a committee can have only one document in debate. No participation aggregate columns exist. Historical participation corrections append; originals remain intact. Enum labels currently match the UI's title-case wording. Award scores are separate chair judgement and will be revisited in the next product phase.

## Authorization

Anonymous authentication creates identity only. `user_access` grants conference, role and optional committee; grants expire and may be revoked. Chair grants require a committee. UI role switching cannot grant database privileges. Every public table has RLS; anonymous callers have no table grants; authenticated users have SELECT only. Writes use `apply_conference_mutation` and its explicitly authorized private transaction boundary. Browser clients cannot edit access grants, receipts or audit records directly.

Private SECURITY DEFINER helpers have pinned search paths, explicit caller checks and restricted execution. The public wrapper and snapshot are SECURITY INVOKER. Read policies check current, non-expired grants. A cached-grant experiment was reverted after a failed sustained-load run; its migration history is preserved. Approval/Logistics document access is restricted by lifecycle state. Access credential hashes remain in a private schema with no browser access.

Development Dashboard: Authentication → Sign In / Providers → Anonymous Sign-Ins must be enabled if using invisible bootstrap. A first browser visit creates an identity but remains an explicitly marked local fallback until an operator grants that exact user. System health shows the user ID in setup details. Grant the intended role/committee with a short expiration through authorized administrative SQL, then reload. Never add self-enrollment or blanket anon policies. Existing dev verification users were granted temporary access only.

## Repository and transactions

Components consume the provider/repository, not Supabase queries. `lib/commands.ts` contains optimistic domain validation, commands and selectors. `SupabaseConferenceRepository` wraps `SupabaseTransport` and `DurableRepository`. The local demo uses the same command model and its own isolated checkpoint. The database independently validates every command and binds its receipt to caller, conference, UUID and payload.

An atomic RPC performs authorization, the domain write, audit entry, receipt and operational notification. Duplicate retries return the original success without another write. Attendance, timer, ballot, document and event edits compare revisions. Queue advance identifies the expected first entry; queue insert ordering is generated by the database. Short committee-scoped locks protect cross-record vote/attendance and queue rules while independent committees proceed independently. Closing a vote validates complete eligible ballots and derives simple-majority or two-thirds outcome (excluding abstentions); withdrawal is explicit. Security Council veto rules are deferred.

## Offline recovery

IndexedDB `conference-os-v3` stores an authoritative checkpoint and an ordered outbox keyed by conference/user. An action UUID is committed locally before the optimistic UI changes. Acknowledgement and updated snapshot are committed together; lost responses retry the same UUID. A conflict is retained for operator review and blocks subsequent sends. Export recovery data before dismissing a conflicting action. Device exports contain personal information and must be protected.

Previously opened Chair routes and assets are cached by the production service worker; Supabase/Auth/API responses are not cached by that worker. Data is in IndexedDB. No service worker is registered in development mode. First prepare the production preview online. Offline context preferences are also in IndexedDB. Confirmed cloud caches older than seven days are pruned; pending changes are never automatically erased. A previously validated identity can reopen offline within a bounded 48-hour authorization lease (or earlier grant expiry). Shared laptops must clear confirmed data after the conference; never clear data while pending operations remain.

Realtime subscribes only to `operational_changes`, filtered to authorized committee scopes or the conference. Subscription reconnection triggers authoritative refetch. Focus/online signals and jittered 60-second recovery reads cover missed notifications. Retry backoff caps at 60 seconds. Timer ticks never hit the server or Realtime. Multi-tab writes use IndexedDB transactions; sync uses Web Locks where available and server idempotency everywhere.

## Capacity and same-IP startup

Supabase documents anonymous creation at 30 requests/IP/hour by default, configurable, with burst capacity tied to the configured value. Therefore fresh anonymous startup for 100 people is NOT ready by default. Reuse sessions and pre-provision/test conference devices before opening. The future access-code exchange must authorize a stable identity, handle replacement laptops deliberately, and avoid a new anonymous signup for every navigation. Review current project limits, configure sufficient measured headroom, and test actual school NAT before release. Never use permissive RLS or client-controlled forwarded IPs as a workaround.

The included 150-client test uses one pre-provisioned identity to exercise operational database/Realtime load. It is explicitly **not** a 150-distinct-user enrollment test. Tail latency and school-network enrollment remain release gates. Prepare isolated fixture SQL with `scripts/prepare-load.mts`, apply only to the guarded development project, then run `npm run test:load`. Sessions/fixture setup files stay ignored. Reports record p50/p95/p99, errors, duplicate counts and reconnect counts. Resource pressure requires Supabase Observability; Data API does not expose CPU.
