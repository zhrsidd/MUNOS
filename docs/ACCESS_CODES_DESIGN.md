# Access-code system design

This document narrows the implementation of staff access codes so the feature can be built without changing Conference OS's authorization model.

## Existing foundation

The database already separates identity from authorization:

- Supabase Auth supplies a per-device `auth.users` identity.
- `public.user_access` grants that identity a conference role and, for Chairs, a committee scope.
- `private.has_access(...)` and RLS remain the authority for every staff read/write.
- `private.access_credentials` exists but is currently unused and private from browser roles.

An access code therefore **redeems into a normal `user_access` grant**. It is not a second authentication or authorization system.

## Device flow

For a cloud build:

1. Reuse the persisted Supabase session if present.
2. If no session exists, create an anonymous Supabase Auth identity for this device.
3. Read the device's active `user_access` grants.
4. If none exist, show the access-code gate instead of a demo/editable workspace.
5. The user enters a code and calls `public.redeem_access_code(conf, code)`.
6. On success the RPC creates/renews the appropriate `user_access` row for `auth.uid()`.
7. Reload the staff shell so the existing repository starts under that real grant.

A second device using the same valid code gets a different Supabase user id and a separate grant. This preserves actor ids, durable outbox ownership, auditability and RLS.

Local/demo builds keep the existing local demo. Public delegate routes such as `/submit/...` and `/amend/...` do not open the staff access gate.

## Code scopes

Create one active code for each operational scope:

- Chair: one code per committee.
- Approval Panel: conference-wide `approval`.
- Admins: conference-wide `logistics`.
- Executive: conference-wide `admin`.

Do not issue an `observer` code in this feature.

The role and committee always come from the matched credential. The redemption caller must never be allowed to supply or choose them.

## Code generation and storage

Codes must be generated by the system, not chosen by staff.

Recommended format: 24 hexadecimal characters (about 96 bits before UUID version-bit loss), displayed as six groups of four, for example:

`A1B2-C3D4-E5F6-789A-BCDE-F012`

Generate the secret from database randomness (for example a stripped `gen_random_uuid()`) and return the formatted raw code **once** from the management RPC.

Normalize redemption input by removing hyphens/spaces and upper-casing it, then require exactly 24 hex characters.

Because the secret is high-entropy and system-generated, store only a SHA-256 digest of the normalized code. PostgreSQL's built-in `pg_catalog.sha256(bytea)` is available on the development project, so this does not require a password-hashing extension or an expensive bcrypt scan. A fast hash is appropriate here only because users cannot choose low-entropy passwords/PINs.

Never store or log the raw code.

## Database additions

Extend `private.access_credentials` only as needed for management metadata (for example `created_by` and `updated_at`). Keep `credential_hash` private.

Add a private redemption-attempt table keyed by authenticated user + conference + timestamp. It exists only for rate limiting and must have no browser policies/grants.

Optionally add a private credential-to-grant link table if the UI needs to revoke already-issued device grants when a credential is compromised. Do not expose the credential id/hash in snapshots.

All new private tables must have RLS enabled and explicit no-browser-access policies consistent with the existing hardening migration.

## RPC contracts

### `public.redeem_access_code(conf uuid, code text) -> jsonb`

- `SECURITY DEFINER`, pinned empty search path, executable by `authenticated` only.
- Require `auth.uid()`.
- Apply failed-attempt rate limiting before expensive/lookup work (suggestion: 8 failures per 10 minutes per user+conference).
- Normalize and hash the supplied code.
- Match exactly one non-revoked, unexpired credential for the conference.
- On wrong/expired/revoked credentials, persist a failed attempt and return the same generic `{status: "invalid"}` result. Do not raise after recording the attempt, because a PostgreSQL exception would roll the rate-limit row back.
- Once the failure threshold is reached, return `{status: "rate_limited"}` without trying a credential.
- On success upsert `public.user_access` for `auth.uid()`, using role/committee/expiry from the credential.
- Return `{status: "ok"}` plus safe metadata only: role, committee id, expiry.
- Never return the hash, credential internals, or raw code.

Anonymous Supabase Auth users still use the database role `authenticated`; a fresh anonymous identity has no access because all existing RLS paths require `user_access`.

### `public.access_code_status(conf uuid) -> jsonb`

Executive-only. Return metadata required by the management UI: credential id, role, committee id/code/name, created time, expiry and active/revoked state. Never return raw code or hash.

### `public.rotate_access_code(conf uuid, role conference_role, committee uuid, expires_at timestamptz) -> jsonb`

Executive-only.

- Permit only Chair / Approval / Logistics / Admin.
- Chair requires a committee in the same conference.
- Other roles must be conference-wide.
- Revoke the previous active credential for that scope.
- Generate + hash a new random code in the database.
- Store only the hash.
- Return the raw formatted code once plus safe metadata.
- If writing an audit entry, details contain only role/scope/expiry; never the code/hash.

### `public.revoke_access_code(conf uuid, credential uuid, revoke_devices boolean) -> void`

Executive-only.

- Revoke the credential so it cannot be redeemed again.
- If `revoke_devices` is true and grant-source linkage is implemented, revoke grants that were issued from that credential.
- If false, existing authorized devices may remain active until their grant expiry.

This explicit choice is safer operationally than making every routine code rotation unexpectedly sign out all prepared devices.

## Expiry

Credential expiry is also the maximum expiry of the resulting `user_access` grant.

The Executive UI should default to a sensible post-conference time but allow an explicit expiry. Do not hard-code DCMUN's 2026 dates in the migration.

Expired or revoked grants must fall back to the existing durable recovery behavior; unsynced local mutations are retained.

## Executive UI

Add an **Access codes** section showing rows for each committee Chair scope plus Approval Panel, Admins and Executive.

Actions:

- Create / Rotate
- Copy the newly generated code (only immediately after creation)
- Revoke
- Optional “also revoke devices using this code” confirmation
- Expiry editor

After the one-time code is dismissed/reloaded, show only metadata and “Generate a new code”; raw codes cannot be retrieved.

## Staff gate UX

Cloud builds with no active grant should show a dedicated gate, not the demo workspace:

- DCMUN / Conference OS
- “Enter staff access code”
- one code input
- Redeem button
- generic invalid/expired message
- explicit rate-limit message when applicable

After redemption, route only to workspaces authorized by active grants. Hiding a workspace is UX only; RLS remains authoritative.

## Security invariants

- No direct browser insert/update grant on `public.user_access`.
- No browser access to `private.access_credentials` or attempt logs.
- No raw codes in snapshots, audit details, console logs, URL query strings, error strings or analytics.
- Do not send code-management commands through the existing general mutation path unless its audit payload is explicitly sanitized; the current path stores command JSON in `audit_log.details`.
- Role/committee are derived from the credential, never the redemption request.
- Keep all existing RLS and `private.has_access` checks.
- High-entropy system-generated codes are mandatory; do not downgrade to short numeric PINs.

## Tests required

Database:

- unassigned authenticated device sees no conference data before redemption;
- valid Chair code grants only its committee;
- Approval/Admins/Executive codes grant only their role;
- wrong, expired and revoked code all fail generically;
- repeated failures rate-limit;
- a second auth user can redeem the same active shared code into a separate grant;
- rotating invalidates the old code;
- only Executive can create/rotate/revoke credentials;
- no raw code/hash appears in audit/snapshot output;
- direct browser access to private credential/attempt tables remains denied.

Client:

- cloud build with no grant renders access gate, not demo workspace;
- successful redemption reloads/opens the authorized workspace;
- expired/revoked access does not discard the durable outbox;
- role switcher/navigation exposes only granted workspaces.

## Deployment rule

Implement and test this in the feature branch/local test database first. Do **not** apply the migration to the shared development Supabase project until the feature PR has been reviewed and rebased onto current `main`.
