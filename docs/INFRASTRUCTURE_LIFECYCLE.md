## Target safeguards to implement and verify before cutover

1. Register the new ref explicitly; do not reuse the old `opmydpozhdgkpcnjwpqb` default or PHESMUN's ref. PHESMUN production remains denied everywhere. Keep exact URL/ref matching, no arbitrary-host acceptance, no permissive fallback and no override flag.
2. Track the project's lifecycle in an owner-controlled register plus a server-enforced production lock/marker inaccessible to test roles. A phase name or allow-list supplied by an agent/process is not authority to demote production. Implement the marker/control path through reviewed committed migrations/configuration; do not invent an existing table or variable.
3. Before promotion, list this ref in **one** nonproduction role only (`DEVELOPMENT_SUPABASE_REFS` or `STAGING_SUPABASE_REFS`), not both, with verified preproduction status. At promotion remove it from every test/development/staging allow-list and activate exact `EXPECTED_SUPABASE_REF` in Production only. The ref must never have simultaneous production and test roles. Keep an owner-controlled production deny-list/registry available to tools without database access, so known-production refusal occurs before connection; the database lock also rejects stale/misclassified test credentials.
4. Load/fixture/reset/destructive tools fail closed for production, missing or unknown phase, contradictory refs, stale lifecycle checks or unavailable verification. After promotion they have no credentials for this ref and no ability to bypass its write boundary. An environment label, changed CLI linking or an old allow-list must not re-authorise tests.
5. Preview builds and server routes fail closed if configured for the promoted ref, both at build time and runtime; health must not contact the database on a refused target. Production requires the exact expected ref, approved candidate and production lifecycle. CI for PRs/branches remains local-only after cutover and receives no production secrets.
6. Enforce the write boundary at the server/database as well as in deployment configuration. Preserve per-user, conference, committee, revocation and mutation checks on every accepted write. A browser's Origin/Referer, CORS, a public API key or a client-side phase flag is **not** proof that a write came from the approved Production app. If the current direct browser-to-RPC transport allows a Preview with a valid production session to write, it does not meet this gate: implement an independently reviewed production-only write gateway/capability with direct bypass denied, while preserving caller identity, RLS-equivalent scoping and existing durable/idempotent semantics. Never solve this by putting a service key in the browser or replacing actor checks with blanket privileged writes. Any gateway must authenticate the actual actor/session, reject cross-site/CSRF attempts, bind any write proof to the intended operation and refuse proof minted by a Preview; a caller-supplied environment header is not a trusted capability. Do not reuse real staff sessions in Preview browsers.

## Formal cutover — human controlled, recorded

Complete the checklist in order during a write-pause window; keep public routes closed until the production build and access boundary pass. A failure leaves the project closed to real-data entry and requires correction, not a temporary test-access exception.

1. Freeze the candidate SHA and migration ledger; reconcile synthetic work/outboxes and retain necessary evidence. Inventory old Previews/aliases, functions/cron/hooks, tests, agent connectors, org/API/database credentials and staff/rehearsal identities.
2. Safely remove synthetic records/Storage objects with a reviewed guarded cleanup on the verified preproduction target; keep migration history and approved configuration. Confirm no real conference data has entered. Retire synthetic submission/amendment links, access codes and grants. Clear test-device state only after its outbox is reconciled; retain UUID/idempotency protections.
3. Disable cloud-agent Supabase/SQL/MCP/Management API test access, Vercel credential access and hosted-test CI/jobs. Revoke agent/test PATs, database roles/passwords, API secret/service-role keys and refresh sessions; remove test `user_access` grants and QR credentials. If a connector's organisation-level access cannot exclude this project, disconnect/revoke that cloud-agent connection rather than assuming a per-project restriction. Replacement production credentials stay with trusted human operators and Production runtime only. Do not give agents newly rotated values.
4. Revocation is not just deleting a local secret or user. Previously issued access JWTs can outlive session revocation: enforce immediate grant/session denial in all relevant RPC/read/write paths, handle legacy key invalidation separately, and wait out any remaining token validity before opening real-data entry if immediate rejection cannot be proved. Existing authenticated production user access is not yet needed; bootstrap it after the transition.
5. Remove all hosted values and secrets from Preview/Development/branch overrides, integration injection, PR CI and agent environments. Rebuild new Previews in local/demo mode. **Retire/delete or otherwise make unreachable every old connected Preview/candidate deployment, immutable URL and alias**; changing defaults does not update a previously built deployment. Ensure none retains a valid server credential, public write proxy or usable production write capability.
6. While writes remain closed, change the owner-controlled lifecycle/register and server lock to production, remove every test allow-list entry and install the exact Production-only expected ref/configuration. Record timestamp, operator, approvals, ref, Small size, candidate SHA, ledger, backup and access-revocation evidence. This is the formal promotion; it does not create another project or replay existing migrations.
7. Release the approved production build from the exact verified code revision with new Production-scoped secrets. Verify target, SHA and health through a human-controlled non-destructive check; confirm old agent access and old/new Previews remain denied. No rehearsal, destructive or synthetic-write suite runs after promotion. Release approval is John Paul Ribeiru's; owner approval covers infrastructure/configuration.
8. Only after all evidence/sign-offs pass, permit actual conference data entry, bootstrap the real Executive and issue real grants/codes/QR links under the approved procedure. Record the known-good application build and compatible ledger. Do not reuse a preproduction build whose embedded target, keys or access boundary differs; a production-configured rebuild needs its own deployment identity/configuration verification.

Any need for remote rehearsal must wait for an owner-approved separate test environment.
