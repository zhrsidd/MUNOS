# Google Drive architecture

Status: **design only.** No Drive API code exists. Today the Chair copies each resolution into the Approval Panel's folder by hand, and Conference OS can store that copy's link. Owner: Claude (integration). Anything touching shared schema or core functions is marked **CODEX REVIEW REQUIRED — DESIGN ONLY**.

## 1. Why Drive exists in Conference OS

| System | Role |
| --- | --- |
| **Supabase** | Authoritative **live operational state**. |
| **Google Docs** | Authoritative **editable resolution content**. |
| **Google Drive** | Conference-owned **documents, archive and fallback** layer. |
| **Conference OS (MUNOS)** | The operational interface across both. |

Drive gives the conference **ownership** of documents (delegates' Docs live in personal accounts), a **readable fallback** when Conference OS is unavailable, and a **tidy archive** after the event. Drive must never become a second live database.

## 2. Supabase vs Google Drive

| Supabase (authoritative, live) | Google Docs / Drive (documents, archive, fallback) |
| --- | --- |
| conferences, committees, schools, delegates, sessions | working resolution Google Docs (delegate-owned) |
| attendance, current/working session | conference-owned Approval copies |
| speaker queues, participation events (incl. POI points), timers | approved / final Docs |
| votes and results | PDF snapshots and printable documents |
| resolution workflow state, submission records, Doc links | committee archive |
| amendment metadata (future, Codex) | generated, read-only exports: roll call, votes, resolution status, end-of-day and final exports |
| group-photo schedule and acknowledgements | emergency human-readable copies |
| audit log, access grants, security, sync/offline state | |

**One-way rule.** Exports flow **from** Supabase **to** Drive. Nobody edits an export and expects Conference OS to change. Every export is stamped "Generated by Conference OS at HH:MM — read only; Conference OS is the record". No staff member should ever maintain the same data in both places; no manually maintained spreadsheets.

## 3. Google Docs as editable resolution content

Delegates write in Google Docs and set *Anyone with the link → Editor* (or share directly with a Chair). Chairs edit there and later type passed amendments into the working Doc. Conference OS stores **document ids only** (`resolution_links.working_doc_id`, `approval_copy_doc_id`) and never reads, parses or edits text. No structured clause editor, no amendment editing, no clause import — now or in this design.

## 4. Folder hierarchy (proposed, simplest practical)

Generate it with `npm run drive:plan -- --conference "DCMUN XVIII" --committees "GA1,GA2,WHO,SC"` (dry run).

```
DCMUN XVIII                          ← Shared Drive owned by DCMUN
├── Committees
│   ├── GA1
│   │   ├── 1 Approval Copies        ← one conference-owned copy per resolution
│   │   ├── 2 PDF Snapshots          ← approved/printed and final PDFs
│   │   └── 3 Exports                ← generated read-only exports (roll call, votes, status)
│   ├── WHO …
│   └── SC …
├── Conference-wide                  ← generated: schedule, schools, group photos, final results
└── System Backups                   ← restricted: database exports
```

Deliberately **not** included from the first sketch:
- **No Approved/Final folders.** Moving files between folders would encode workflow state in Drive and drift from Supabase. State lives in Conference OS; a file's stage is in its name and Drive metadata (`GA1-04 · Approved.pdf`, `GA1-04 · Final (Passed).pdf`).
- **No Amendments folder.** Amendments are applied inside the working Doc; amendment records live in Supabase.
- **No separate roll-call/voting/backup folders per committee.** One *Exports* folder per committee is enough; file names carry the type and day.
- **No folder per resolution.** One copy + snapshots per resolution sit side by side, named by code.

## 5. Committee-folder mapping

- The **authoritative mapping is stored ids**: conference → root folder id; (committee, purpose) → folder id. Names are for humans and may be renamed in Drive without breaking anything.
- Each folder created by Conference OS is tagged with Drive `appProperties` (`munosKey=committee:<committee-uuid>:approval`, `munosConference=<uuid>`). The tag is used **only to reconcile** after an ambiguous failure (did the create succeed before the timeout?), never as the normal lookup.
- The dry-run planner uses committee **codes** in keys for readability; the real mapping uses committee **UUIDs**, so renaming a committee code does not orphan its folder.

## 6. Resolution lifecycle (future automation)

```
Delegate working Google Doc (delegate-owned)
  → Anyone with the link → Editor (or shared directly with a Chair)
  → registered in Conference OS via QR (Draft, with the Chair)            ← implemented
  → Chair reviews/edits in Google Docs                                    ← implemented (manual)
  → Chair clicks Submit to Approval (Draft → Submitted)                   ← implemented
  → Conference OS creates a conference-owned copy in GA1/1 Approval Copies ← FUTURE (today: Chair copies by hand, may paste the link)
  → Approval Panel works from that copy; approves                         ← implemented (state)
  → PDF snapshot "Approved" in GA1/2 PDF Snapshots (print source)          ← FUTURE
  → printed → debate → vote (amendments typed into the working Doc)       ← implemented / Codex
  → PDF snapshot "Final (Passed|Failed)" of the working Doc               ← FUTURE
```

**Access.** Delegates set their Doc to *Anyone with the link → Editor* (or share directly with a Chair when their school forbids link sharing). Human Chairs and the automation are separate concerns: an authenticated automation identity can read a Doc shared with "anyone with the link", but not a Doc shared only with a Chair or one blocked by the owner's school policy — those become *Needs attention* and the Chair copies manually. No committee mailbox or Google Group is used. Full analysis, identity choice and setup: [GOOGLE_WORKSPACE_ACCESS_MODEL.md](GOOGLE_WORKSPACE_ACCESS_MODEL.md).

## 7. Approval copies

- Created with Drive `files.copy` into the committee's *Approval Copies* folder (`supportsAllDrives=true`), named `GA1-04 · <title>`, tagged `appProperties {munosResolution, munosPurpose:'approval-copy'}`.
- The new file id is written to `resolution_links.approval_copy_doc_id` (already exists). If the Chair already pasted a manual copy link, automation **does nothing** (manual wins; no duplicate).
- The Approval Panel works only on the conference-owned copy, so the delegate cannot change the text under review.

## 8. PDF snapshots

- `files.export(docId, 'application/pdf')` → upload into *PDF Snapshots*, tagged `{munosResolution, munosStage:'approved'|'final', munosRevision}`.
- Snapshots are **outputs**: print source, archive, fallback. Never edited, never authoritative.
- One snapshot per (resolution, stage). Re-export on retry **updates the same file** (new Drive revision), it does not add files.

## 9. Attendance / voting exports

- Generated from Supabase on demand (Executive button) and at end of day: `Roll call · GA1 · Day 2.csv`, `Votes · GA1 · Day 2.csv`, `Resolution status · GA1.csv`; conference-wide `Final results.csv`.
- Same file updated in place per (committee, kind, day); stamped read-only; staff get **viewer** access.
- Never imported back.

## 10. Emergency fallback

If Conference OS is down and Google works: Chairs and Approval use *Approval Copies*, the delegates' working Docs, the latest *Exports* (who was present, results so far) and printed sheets. Record on paper; don't build parallel spreadsheets; one person re-enters into Conference OS afterwards.

If Google is down and Conference OS works: every live operation continues; only document access waits (see the runbook).

## 11. Failure and retry behaviour

**Drive failure never blocks a conference operation.**

```
operational change commits in Supabase (e.g. Draft → Submitted)      ← always succeeds independently
  → Drive side effect queued as a job (pending)
  → worker attempts it (syncing)
      success → synced (file id stored)
      failure → failed — will retry (backoff 1, 2, 5, 10, 30 min…)
      repeated failure (e.g. 8 attempts / 2 h) → failed — needs attention (Executive sees it; Retry button)
```

Plain-language states shown to staff:

| State | Shown as |
| --- | --- |
| Drive not set up for this conference | **Not configured** |
| Job created, not yet attempted | **Pending** |
| Worker is running it | **Syncing** |
| Done; file id stored | **Synced** |
| Last attempt failed, will retry | **Failed — will retry** |
| Retries exhausted / permission problem | **Needs attention** (with a plain reason: "Conference OS can't open the delegate's Doc — ask the delegation to set Anyone with the link → Editor") |

System health gains a *Drive* row: GREEN when synced, YELLOW when jobs are failing or pending too long — **never RED** (Drive is not required for the conference to run).

Trigger: the worker runs (a) right after a relevant action via a server route, (b) on a schedule (Vercel Cron; per-minute schedules need Vercel Pro — on Hobby rely on (a) and (c)), (c) when the Executive presses *Retry now*.

## 12. Idempotency

| Operation | How retries stay safe |
| --- | --- |
| Folder setup ("ensure") | For each planned key: stored id exists and folder not trashed → keep. Else look for a folder tagged `munosKey` under the parent → adopt it. Else create with the tag. Running it twice creates nothing new. |
| Approval copy | Job idempotency key `approval-copy:<resolution>`. Skip if `approval_copy_doc_id` is set. Before copying after an *ambiguous* failure (timeout), search the folder for `appProperties munosResolution=<id> and munosPurpose='approval-copy'` and adopt it. |
| PDF snapshot | Key `snapshot:<resolution>:<stage>`. Update the existing tagged file's content instead of creating another. |
| Exports | Key `export:<committee>:<kind>:<day>`. Update in place. |
| Concurrency | Jobs claimed with a short lease (`for update skip locked`), so two workers never run the same job. |
| Destructive actions | None. The integration never deletes or moves delegate Docs and never trashes files automatically. |

Stable Drive ids are authoritative; name search is never the normal mapping.

## 13. Security and credentials

- **Identity:** a dedicated Google Cloud service account (preferred) or, if DCMUN policy refuses it as a Shared Drive member, a dedicated Workspace automation user — see [GOOGLE_WORKSPACE_ACCESS_MODEL.md](GOOGLE_WORKSPACE_ACCESS_MODEL.md) §9. Added to the conference Shared Drive as **Contributor** (create and edit; cannot move or trash). No domain-wide delegation; it reaches only Docs shared with "anyone with the link" and the Shared Drive.
- **Credential storage:** prefer **Vercel OIDC → Google Workload Identity Federation** (no long-lived key). Fallback: a service-account JSON key in a **Sensitive**, server-only Vercel variable. Never `NEXT_PUBLIC_*`, never in the repository, never sent to browsers.
- **Scope:** `https://www.googleapis.com/auth/drive` (needed to copy Docs shared with the account), limited in practice by what is shared with the service account.
- **Server routes** that trigger Drive work verify the caller (Supabase session + Executive/Chair grant, or the Vercel `CRON_SECRET`). No unauthenticated Drive endpoint.
- **People:** Executive + technical contact manage the Shared Drive. Chairs get their committee folder; Approval Panel gets the *Approval Copies* folders; *System Backups* stays restricted. Exports are view-only for staff.
- Personal data: exports contain delegate names (no emails unless needed). Device recovery files are never stored in shared folders.

## 14. Shared Drive recommendation

Use a **Google Shared Drive owned by the DCMUN Google Workspace** (not a personal "My Drive"):
- files belong to the organisation and survive staff leaving;
- membership-based access is easy to audit and revoke after the conference;
- the service account can be a member without anyone sharing a personal account.

If DCMUN has no Workspace with Shared Drives, use one dedicated conference Google account that owns a top-level folder, and plan to transfer ownership after the event.

## 15. What NOT to put in Drive

- Live state (attendance, queues, votes, workflow status) as an **editable** source — exports only.
- Manually maintained spreadsheets that duplicate Conference OS.
- Credentials, access grants, submission-link tokens, service keys.
- Device recovery files (personal data, operational state) outside *System Backups*.
- Copies of delegates' Docs in folders that encode workflow state.

## 17. CODEX REVIEW REQUIRED — DESIGN ONLY

Nothing below is implemented. These are the minimal additions the integration would need.

**A. Folder mapping** (new table)

```sql
-- DESIGN ONLY
create table public.drive_folders (
  conference_id uuid not null references public.conferences(id),
  committee_id  uuid null,                 -- null = conference-level folder
  purpose text not null check (purpose in ('root','committees','committee','approval','snapshots','exports','conference_wide','system_backups')),
  folder_id text not null,                 -- Drive id (authoritative)
  created_at timestamptz not null default now(),
  unique nulls not distinct (conference_id, committee_id, purpose)
);
-- RLS: select for admin; committee rows also for that committee's chair. Writes only by the server (service_role).
```

**B. Drive jobs** (new table, or a generalisation of the existing core `public.archive_jobs`, which already has pending/synced/failed, attempts, `archive_id`, `last_error` keyed by document version)

```sql
-- DESIGN ONLY
create table public.drive_jobs (
  id uuid primary key default gen_random_uuid(),
  conference_id uuid not null, committee_id uuid,
  kind text not null check (kind in ('ensure_folders','approval_copy','pdf_snapshot','export')),
  subject_id uuid,                          -- resolution / committee
  idempotency_key text not null unique,     -- e.g. 'approval-copy:<resolution>'
  state text not null default 'pending' check (state in ('pending','syncing','synced','failed','attention')),
  attempts int not null default 0, next_attempt_at timestamptz not null default now(), lease_until timestamptz,
  result_file_id text, last_error text,     -- plain-language reason for staff
  created_at timestamptz not null default now(), updated_at timestamptz not null default now()
);
-- RLS: select for admin and the committee's chair (status chips); writes only by the server.
```

Codex decision needed: reuse/generalise `archive_jobs` (version-scoped) vs. a new `drive_jobs` (resolution/committee-scoped).

**C. How jobs are created — preferred: no core change.** A **reconciler** in the worker derives desired state from Supabase (e.g. resolutions in `Submitted` or later with a `working_doc_id` and no `approval_copy_doc_id`) and upserts jobs by idempotency key. This avoids touching `private.apply_mutation`. The alternative — inserting a job inside the core `Draft → Submitted` transition (transactional outbox) — is faster but modifies the core command function and needs Codex review.

**D. Snapshot references.** Either `drive_jobs.result_file_id` per (resolution, stage), or two nullable columns on Claude's `resolution_links` (`approved_pdf_file_id`, `final_pdf_file_id`).

**E. Read model.** Add `driveFolders` (committee → folder ids, for "Open committee folder" links) and per-resolution Drive status to Claude's `operations_snapshot`.

**F. Server API** (all server-only, authenticated):
- `POST /api/drive/setup` — Executive; ensure folders (idempotent).
- `POST /api/drive/sync` — Executive *Retry now*, post-action kick, or Vercel Cron with `CRON_SECRET`; claims and runs due jobs.
- Env: `GOOGLE_DRIVE_SHARED_DRIVE_ID`, OIDC settings (`GCP_PROJECT_NUMBER`, `GCP_WORKLOAD_IDENTITY_POOL`, `GCP_SERVICE_ACCOUNT_EMAIL`) or `GOOGLE_SERVICE_ACCOUNT_KEY` (Sensitive), `CRON_SECRET`.

**G. Amendments (Codex).** Only workflow flags ("passed, not yet applied" / "applied to working Doc"); no Drive or Docs editing.
